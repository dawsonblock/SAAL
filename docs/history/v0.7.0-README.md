# SAAL-RSI v0.7.0 — Full Corrected Research Integration

**Status: runnable, synthetic-only research reference. NOT a general alignment guarantee or production-safe autonomous agent.**

This release integrates the *two user-supplied source packages*: **SAAL v0.5.0** and **Dream-RSI Governed v1.0.0**, preserving the source modules, test suites, docs and non-code upstream references in distinct directories. The third package, `saal_rsi`, is the new bounded integration.

## What is integrated — and what is not

- SAAL's hidden-goal synthetic appointment laboratory, explicit clarification, guarded `schedule.propose` and simulated execution are used as **the actual candidate evaluator**. The actor sees only `Scenario.public_view()`, never the hidden objective or evaluation oracle.
- Dream-RSI's `ReplayWorld`, `ReplayEngine`, `RiskAwareUCBPolicy` and `FixedBreadthPolicy` are used to **search for experiment strategies** from *development-only* outcome records. The previous policy-specific RNG confound is corrected by common per-action outcome streams.
- A **closed candidate schema** restricts research proposals to a frozen, rule-based SAAL actor with a finite `ask_cost` parameter. Research proposals cannot submit arbitrary code, disable control, gain new tools, or switch models.
- A distinct **selection** partition ranks replay-discovered candidates. The proposal contains *no private holdout seeds*, no private evaluator keys, and absolutely no claim of qualification.
- An **evaluator-owned holdout** reruns candidates and a matched frozen baseline on new simulated cases; includes OOD, corrections, reward-proxy disagreement, hostile injected instructions, and per-seed paired bootstrap uncertainty. A candidate with non-positive lower bound or a safety regression is rejected.
- A separate evaluator Ed25519 key **signs positive or negative qualification evidence**, with exact candidate and proposal digests and implementation fingerprint. A signed report **never confers runtime or promotion authority**.
- The original `saal` and `dream-rsi` CLIs remain available; `saal-rsi` is an independent integrated experiment workflow.

## Reproducible example: research / evaluator separation

**Development / proposer workstation** (these seeds are public synthetic *development* data):

```bash
saal-rsi discover --out artifacts/proposal.json \
  --development-seeds 111,112,113 --selection-seeds 211,212,213 \
  --worlds 3 --episodes 8
```

**Evaluator-controlled workstation** (use an isolated machine/UID and private files in genuine experiments):

```bash
saal-rsi keygen --out private/evaluator.ed25519
# Record the displayed public_key_hex separately and protect the private key.
saal-rsi plan-create --out private/holdout.json --episodes 100
# Independently timestamp/publish the displayed private_plan_commitment *before* examining candidate results.
# Only transfer the proposal to the evaluator. NEVER transfer the private plan/key to a researcher.
saal-rsi qualify --proposal artifacts/proposal.json \
  --private-plan private/holdout.json \
  --signing-key private/evaluator.ed25519 \
  --out private/signed-qualification.json
```

**Independent verifier**, using the *pinned public key* from the evaluator's trusted key-distribution channel:

```bash
saal-rsi verify --report signed-qualification.json \
  --proposal proposal.json --public-key YOUR_PINNED_64_HEX_CHARACTER_PUBLIC_KEY
```

`verify` validates the signature and candidate binding. A signed negative report can legitimately verify as `true`; check `qualification_passed` separately. `promotion_allowed` always remains `false` in this version.

## Important scientific findings

Replay scores reflect performance **only on recorded development histories**. They do not guarantee improvement on new users, unknown goals, or future environments. The holdout synthetic oracle is artificial; regret is not a measurement of human welfare. With the default configuration, improvements frequently **fail** strict independent qualification. Such rejections are correct results, not errors.

In this package, **SAAL controls task proposals** (non-binding synthetic scheduling actions only) and **Dream-RSI controls research scheduling only**. Neither can change hard safety rules, provide actual external booking services, deploy models, or access private verifier signatures.

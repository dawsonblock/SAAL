# Implementation, migration and limitations

## Preserved history and version boundaries

`provenance/v0.9.3-historical-freeze.json` binds the input v0.9.2 ZIP and every preserved historical file. Tests verify their bytes, including `model_worker.py` and archived negative reports. The old worker is unchanged. Job-v2/v3 retain their original 128-byte, five-label semantics and three-file artifact inventory. They cannot process job-v4.

Job-v4 binds a closed `ModelSpec`, public DatasetRecordV2 manifest, initialization seed, optimizer settings, class-balancing policy, sequence limit, worker source inventory and GPU dependency-lock digest. Model architecture, tokenizer, positions, rank, targets or data cannot be substituted after admission. The new head has CHEAP, FAST, ASK and REFUSE. Legacy FORBIDDEN remains valid in historical validation and negative behavior tests. Its absence from the new head is a structural restriction, not evidence of learned safety.

The model's bounded variants are dimensions 32/64, one/two layers and 128/256 input bytes; the reference experiment uses 64 dimensions, two layers, four heads and a 256-dimensional feedforward block. SDPA boolean `True` allows attention; masked padding keys are excluded and evaluation dropout is explicitly zero, following [PyTorch documentation](https://docs.pytorch.org/docs/2.10/generated/torch.nn.functional.scaled_dot_product_attention.html). Training uses deterministic math SDPA and declares CPU/GPU reload tolerances of absolute/relative 1e-4 with exact decisions.

## Matched learning branches

For each preregistered initialization seed, supervised backbone training uses the same public training population. Query/value adapters are frozen at zero effect during backbone training. A chosen backbone is exported without rank-dependent adapter tensors, allowing rank-4 and rank-8 branches to share exactly the same checkpoint bytes.

Frozen evaluation, full backbone tuning, rank-4 LoRA and rank-8 LoRA receive the same frozen backbone and disclosed data. Full tuning changes backbone tensors with adapters fixed; LoRA changes only the admitted query/value low-rank matrices. The fixed-budget branches use AdamW and weighted cross-entropy. Unweighted loss and balanced sampling are implemented as explicit job alternatives; their superiority is not established by the reference campaign.

Development selection fixes this order: no unauthorized public regression proposals, no regression-family accuracy loss, nonzero correct examples in every class, worst-category/family accuracy, family-macro accuracy, and complete counterfactual-pair accuracy. Ties within training choose the earliest equally scoring checkpoint; cross-candidate ties prefer fewer trainable parameters and measured run time. A checkpoint may still fail development targets. Selection does not manufacture qualification or hide failed runs.

The public dataset varies preference reversals, negation, conditional authorization, conflicting speakers, missing goals, revoked permission, misleading proxy scores, corrections and action scope. It includes both CHEAP and FAST. Recipes and parent relationships disclose correlations. Separate wording per public partition does not establish semantic independence; all examples share a synthetic oracle/operator. Unknown terms require definitions; merely inserting new words is not a transfer test.

Metrics include accuracy by category/family, worst family, four-class confusion, class coverage, complete-pair accuracy, critical errors, unauthorized proposals and multiclass Brier score. Family-level effect intervals and qualification statistics remain in the existing evaluation plane. Neural probabilities are not asserted to be calibrated.

## Artifacts and trust

Result-v3 has an exact 16-file inventory: experiment manifest, signed job, dataset manifest, ModelSpec, backbone, adapter, full candidate, checkpoint selection, training JSONL, runtime identity, resource accounting, tensor inventory, cleanup evidence, CPU replay evidence, artifact inventory and result. Every tensor must have an admitted name, shape and float32 dtype and finite values. Full candidate/adapter consistency and frozen backbone equality are checked even after hashes have been recomputed. Controller-side CPU reconstruction checks disclosed decisions and logits.

Worker outputs remain untrusted. The controller appends cleanup evidence after its own process/session checks and recomputes inventory bindings; the worker cannot attest that a cloud session stopped. Runtime reports and signatures are measured identity claims, not hardware attestation. A dishonest worker/evaluator or same-UID administrator can falsify reports, inspect files or roll back local databases. Subprocess isolation reduces accidental state sharing but is not an OS security sandbox. Separate users/machines, authenticated services and externally anchored ledgers remain necessary for independent assurance.

## Colab campaign lifecycle

One named session runs the preregistered campaign. Provisioning, reviewed worker-source upload, fresh hash-locked environment installation, training, result retrieval, log export, stop and absence verification are monitored. A local coordinator validates each backbone and signs its adaptation jobs; it never transfers its private key, custody/evaluator keys or protected labels. Each run has a unique remote output directory and durable local reservation. The signed campaign allows at most two retries of the same download for transient service errors, within its original deadline; these retries never restart training. Completed outcomes are persisted after each run. Credential-bearing runtime proxy URLs are removed from saved monitoring output. OOM, deadline or interruption terminates the campaign and preserves negative outcomes; no silent retries or altered batches occur. A separate watchdog stops only the exact admitted session. Failed stop/status requests preserve an unresolved cleanup incident.

The official [Google Colab CLI](https://github.com/googlecolab/google-colab-cli) provides the named-session operations. The controller currently expects `uv` and Python 3.13 in the runtime and rejects incompatible assignments. There is no provider-side monetary cap. Installer hashes verify downloaded distributions; pinned installed versions alone are weaker evidence.

## Continual learning and qualification

`continual_learning.py` implements public sequential LoRA adaptation, optional fixed replay ratios, before-task probes, a full retention matrix and matched fresh-adapter controls, with bounded steps/time. It reports forgetting, backward/forward transfer, parameter count, tokens and per-task adaptation gain. Testing the measurement implementation is distinct from completing a credible multi-task transfer study. Replay selection is a simple deterministic subset, not a proven efficient policy. Dynamic rank, adapter routing, pretrained LLM/QLoRA and recursive self-modification remain deferred.

New-model inference dispatch reaches the existing family custody/qualification workflow. Legacy case-number qualification is prohibited for v4. Public fixtures cannot satisfy protected provenance or independent custody gates, even with perfect predictions. The existing minimum family counts, sign test, alpha allocations, safety/error bounds, regression constraints and one-use receipt consumption remain unchanged. No independently managed custodian or evaluator has qualified the shipped models. External activation remains prohibited.
